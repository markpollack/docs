## How ACP Works

ACP uses a subprocess model by default. A **client** (your application, or an editor like Zed) launches an **agent** as a child process and communicates over stdin/stdout using JSON-RPC messages. An agent can also run remotely and accept connections over HTTP or WebSocket (see [Remote agents](#remote-agents-over-streamable-http)); the messages are the same. The protocol has three phases:

1. **Initialize** — client and agent exchange protocol versions and capabilities
2. **Session** — client creates a session with a working directory context
3. **Prompt** — client sends messages, agent streams back responses

## Overview

The ACP Java SDK provides:

- **Client SDK** — connect to and interact with any ACP-compliant agent
- **Agent SDK** — build ACP-compliant agents that work in Zed, JetBrains, and VS Code
- **Test utilities** — in-memory transports for fast, deterministic testing

## Quick Start

### Try it now

The fastest way to see ACP in action is to clone the tutorial and run a module. The client example talks to the [Grok CLI](https://github.com/xai-org/grok-cli) (signed in once with `grok login`; no API key needed). The agent example runs locally with no API key either.

```bash
git clone https://github.com/markpollack/acp-java-tutorial.git
cd acp-java-tutorial

# Client: talk to Grok as an ACP agent
./mvnw exec:java -pl module-01-first-contact

# Agent: build and run your own (no API key needed)
./mvnw package -pl module-12-echo-agent -q
./mvnw exec:java -pl module-12-echo-agent
```

### Client — Connect to an Agent

This example launches the [Grok CLI](https://github.com/xai-org/grok-cli) as an ACP agent subprocess and sends it a prompt. Any CLI tool that speaks ACP over stdin/stdout works here; Grok is one such tool.

`AgentParameters` builds the command line (`grok agent stdio`). `StdioAcpClientTransport` spawns the process and handles the JSON-RPC framing. The `sessionUpdateHandler` receives the agent's response text as it streams in — without it, you'd get the stop reason but no visible output.

```java
import com.agentclientprotocol.sdk.client.*;
import com.agentclientprotocol.sdk.client.transport.*;
import com.agentclientprotocol.sdk.spec.AcpSchema.*;
import java.util.List;

// Launch the Grok CLI as an ACP agent subprocess
var params = AgentParameters.builder("grok").arg("agent").arg("stdio").build();
var transport = new StdioAcpClientTransport(params);

AcpSyncClient client = AcpClient.sync(transport)
    .sessionUpdateHandler(notification -> {
        // Print the agent's response as it streams in
        if (notification.update() instanceof AgentMessageChunk msg) {
            System.out.print(((TextContent) msg.content()).text());
        }
    })
    .build();

client.initialize();
// ACP requires cwd to be an absolute path; agents may reject "."
var session = client.newSession(new NewSessionRequest(System.getProperty("user.dir"), List.of()));

var response = client.prompt(new PromptRequest(
    session.sessionId(),
    List.of(new TextContent("What is 2+2? Reply with just the number."))
));

System.out.println("\nStop reason: " + response.stopReason());
client.close();
// Output: 4
// Stop reason: end_turn
```

### Agent — Build Your Own

This is the other side of the conversation. When you build an agent, **editors and clients launch your code** as a subprocess and send it JSON-RPC messages over stdin. Your agent handles three request types: initialize, new session, and prompt.

The stdio transport reads from stdin and writes to stdout. `run()` blocks until the client disconnects. The module includes a demo client that launches this agent as a subprocess and exercises it — you'll see `Echo: Hello!` printed when you run it.

```java
import com.agentclientprotocol.sdk.annotation.*;
import com.agentclientprotocol.sdk.agent.SyncPromptContext;
import com.agentclientprotocol.sdk.agent.support.AcpAgentSupport;
import com.agentclientprotocol.sdk.agent.transport.StdioAcpAgentTransport;
import com.agentclientprotocol.sdk.spec.AcpSchema.*;
import java.util.UUID;

@AcpAgent
class EchoAgent {

    @Initialize
    InitializeResponse init() {
        return InitializeResponse.ok();
    }

    @NewSession
    NewSessionResponse newSession() {
        return new NewSessionResponse(UUID.randomUUID().toString(), null, null);
    }

    @Prompt
    PromptResponse prompt(PromptRequest req, SyncPromptContext ctx) {
        ctx.sendMessage("Echo: " + req.text());
        return PromptResponse.endTurn();
    }
}

// Reads JSON-RPC from stdin, writes to stdout — editors connect here
AcpAgentSupport.create(new EchoAgent())
    .transport(new StdioAcpAgentTransport())
    .build()
    .run();
```

Run this yourself: [Module 12: Echo Agent](https://github.com/markpollack/acp-java-tutorial/tree/main/module-12-echo-agent) — includes a demo client that launches the agent and sends test prompts. No API key required.
</Tip>

### Adding the SDK to your project

`acp-core` holds the client and agent SDKs and the stdio, WebSocket, and Streamable HTTP client transports. From 0.18.0 it contains no JSON implementation, so add one JSON module next to it:

```xml
<dependency>
    <groupId>com.agentclientprotocol</groupId>
    <artifactId>acp-core</artifactId>
    <version>0.80.0</version>
</dependency>
<!-- Jackson 2 (com.fasterxml.jackson.databind) -->
<dependency>
    <groupId>com.agentclientprotocol</groupId>
    <artifactId>acp-json-jackson2</artifactId>
    <version>0.80.0</version>
</dependency>
<!-- or Jackson 3 (tools.jackson.databind), for example alongside Spring Boot 4 -->
<!--
<dependency>
    <groupId>com.agentclientprotocol</groupId>
    <artifactId>acp-json-jackson3</artifactId>
    <version>0.80.0</version>
</dependency>
-->
```

<Warning>
**Upgrading from 0.17 or earlier on `acp-core` alone?** Without a JSON module, `AcpJsonMapper.createDefault()` fails at runtime with `No AcpJsonMapperSupplier found on the classpath`. `acp-agent-support`, `acp-test`, and `acp-streamable-http-jetty` already bring `acp-json-jackson2`, so users of those modules need nothing more. Both JSON modules write the same bytes on the wire; with both on the classpath, Jackson 3 wins.
</Warning>

<Note>
0.80.0 runs on the classpath and is not yet JPMS-modular (no `module-info`): two packages,
`com.agentclientprotocol.sdk.agent.transport` and `com.agentclientprotocol.sdk.json`, are split across
more than one jar (`acp-core` plus `acp-streamable-http-jetty`, and `acp-core` plus
`acp-json-jackson2`/`acp-json-jackson3`, respectively), which JPMS doesn't allow for one package. A fix
is planned after 0.80.0.
</Note>

For annotation-based agents (as shown above), add `acp-agent-support` instead — it includes `acp-core` and `acp-json-jackson2` transitively:

```xml
<dependency>
    <groupId>com.agentclientprotocol</groupId>
    <artifactId>acp-agent-support</artifactId>
    <version>0.80.0</version>
</dependency>
```

### Remote agents over Streamable HTTP

An agent does not have to be a subprocess. From 0.18.0 the SDK implements the ACP [Streamable HTTP and WebSocket transport](https://agentclientprotocol.com/rfds/streamable-http-websocket-transport): the agent listens on an HTTP endpoint, and any number of clients connect to it over HTTP POST with Server-Sent Event streams, or over a WebSocket upgrade on the same path. Each connection gets its own agent. Plain `http://` (for example on localhost) is a first-class deployment.

**Agent** — add `acp-streamable-http-jetty`:

```xml
<dependency>
    <groupId>com.agentclientprotocol</groupId>
    <artifactId>acp-streamable-http-jetty</artifactId>
    <version>0.80.0</version>
</dependency>
```

`StreamableHttpAcpAgentTransport` runs an embedded Jetty listener and creates one fresh agent per remote connection through an `AcpAgentFactory`. The agent definition is the same builder you would use over stdio:

```java
import com.agentclientprotocol.sdk.agent.AcpAgent;
import com.agentclientprotocol.sdk.agent.AcpAgentFactory;
import com.agentclientprotocol.sdk.agent.transport.StreamableHttpAcpAgentTransport;
import com.agentclientprotocol.sdk.json.AcpJsonMapper;
import com.agentclientprotocol.sdk.spec.AcpSchema.*;
import java.util.UUID;

// One fresh agent per remote connection
AcpAgentFactory agents = AcpAgentFactory.sync(transport -> AcpAgent.sync(transport)
    .initializeHandler(req -> InitializeResponse.ok())
    .newSessionHandler(req -> new NewSessionResponse(UUID.randomUUID().toString(), null, null))
    .promptHandler((req, ctx) -> {
        ctx.sendMessage("Echo: " + req.text());
        return PromptResponse.endTurn();
    })
    .build());

var server = new StreamableHttpAcpAgentTransport(8080, AcpJsonMapper.createDefault(), agents);
server.start().block();            // serves http://localhost:8080/acp and ws://localhost:8080/acp
server.awaitTermination().block();
```

**Client** — `StreamableHttpAcpClientTransport` is in `acp-core`. Everything after the transport is the same client code as over stdio:

```java
import com.agentclientprotocol.sdk.client.AcpClient;
import com.agentclientprotocol.sdk.client.AcpSyncClient;
import com.agentclientprotocol.sdk.client.transport.StreamableHttpAcpClientTransport;
import com.agentclientprotocol.sdk.json.AcpJsonMapper;
import com.agentclientprotocol.sdk.spec.AcpSchema.*;
import java.net.URI;
import java.util.List;

var transport = new StreamableHttpAcpClientTransport(
    URI.create("http://localhost:8080/acp"), AcpJsonMapper.createDefault());

AcpSyncClient client = AcpClient.sync(transport)
    .sessionUpdateHandler(notification -> {
        if (notification.update() instanceof AgentMessageChunk msg) {
            System.out.print(((TextContent) msg.content()).text());
        }
    })
    .build();

client.initialize();
var session = client.newSession(new NewSessionRequest(".", List.of()));
var response = client.prompt(new PromptRequest(
    session.sessionId(), List.of(new TextContent("Hello over HTTP!"))));

System.out.println("\nStop reason: " + response.stopReason());
client.close();
// Output: Echo: Hello over HTTP!
// Stop reason: END_TURN
```

A `WebSocketAcpClientTransport` pointed at `ws://localhost:8080/acp` talks to the same agent unchanged.

**Mounting in your own server** — `StreamableHttpAcpServlet` (module `acp-http-servlet`) serves Streamable HTTP, SSE and the WebSocket upgrade together, in any Servlet 6 container (Spring Boot, Tomcat, Jetty, Undertow) at a path you choose. Register it with async support. In Spring Boot:

```java
import com.agentclientprotocol.sdk.agent.AcpAgentFactory;
import com.agentclientprotocol.sdk.agent.transport.StreamableHttpAcpServlet;
import com.agentclientprotocol.sdk.json.AcpJsonMapper;
import org.springframework.boot.web.servlet.ServletRegistrationBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class AcpServletConfig {

    @Bean
    ServletRegistrationBean<StreamableHttpAcpServlet> acpServlet(AcpAgentFactory agents) {
        var registration = new ServletRegistrationBean<>(
            new StreamableHttpAcpServlet(AcpJsonMapper.createDefault(), agents), "/acp");
        registration.setAsyncSupported(true);
        return registration;
    }
}
```

The container's lifecycle drives the servlet: `init()` starts the SSE keep-alive and `destroy()` closes every connection, cancelling in-flight prompts. The servlet upgrades WebSocket requests itself, through the container's own Jakarta WebSocket 2.1 support, on the same path; a container with none answers the upgrade `501`.

<Note>
The `acp-websocket-jetty` module and its single-client `WebSocketAcpAgentTransport` were deprecated for removal in 0.18.0 and are **removed in 0.80.0**. Use `StreamableHttpAcpAgentTransport` as shown above, which serves the WebSocket upgrade for any number of clients, one agent per connection; see the [0.80.0 migration guide](/docs/acp-java-sdk/migration-0.80) for the full change.
</Note>

### Release history

Version `0.18.0` adds remote agents over the Streamable HTTP and WebSocket transport and splits JSON into `acp-json-jackson2` and `acp-json-jackson3`; see [What's New](/docs/acp-java-sdk/whats-new) for the three changes to check when upgrading. Versions `0.15.0` through `0.17.0` changed no public API. Version `0.12.0` added session/list, session/close, session/resume, elicitation, session/fork, and session/set_config_option. Version `0.14.0` (superseding the never-released 0.13.0) adds logout, session/delete, additional workspace directories, per-chunk message IDs, and the unstable providers/* configuration methods, promotes session/set_config_option to stable, and deprecates the removed session/set_model API (use session/set_config_option with a `"model"` category option). Version `0.80.0` is binary-incompatible with 0.18.0 and removes `session/set_model` and `acp-websocket-jetty`; see the [0.80.0 migration guide](/docs/acp-java-sdk/migration-0.80) for every breaking change. See the [API Reference](/docs/acp-java-sdk/reference/java#installation) for installation.

## Three Agent API Styles

| Style | Entry Point | Best For |
|-------|-------------|----------|
| **Annotation-based** | `@AcpAgent`, `@Prompt` | Least boilerplate, declarative style |
| **Sync** | `AcpAgent.sync()` | Blocking handlers, plain return values |
| **Async** | `AcpAgent.async()` | Reactive applications, Project Reactor `Mono` |

All three styles produce identical protocol behavior. Choose based on programming preference.
