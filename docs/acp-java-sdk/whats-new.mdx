## 0.80.0 (unreleased)

<Warning>
**This version has not shipped yet.** This entry describes a release candidate under active
verification; version numbers, dates and content may still change before it's tagged. Don't treat
anything below as available until the [migration guide](/docs/acp-java-sdk/migration-0.80) and this
page say otherwise.
</Warning>

0.80.0 implements the full stable ACP schema (v1.9.1), end to end, and is the clearest sign yet that
**0.80 marks the road to 1.0**. It's binary-incompatible with 0.18.0: recompile against it, don't just
swap the jar. The full breaking-change list, with a quick-mapping table from the old API to the new
one, is in the [migration guide](/docs/acp-java-sdk/migration-0.80).

**This SDK is checked against the protocol itself, not just its own tests.** The Java client and agent
run a cross-SDK interop suite against the TypeScript, Rust, Python and Kotlin SDKs over stdio,
Streamable HTTP and WebSocket. See [Cross-SDK Compatibility](/docs/acp-java-sdk/compatibility) for
exactly what's tested, what isn't yet, and how the feature set compares.

**One protocol core, mounted natively into your framework.** All of ACP's protocol rules live in a
single framework-neutral core; each framework integration is a thin host that serves ACP on the
framework's own server, port, TLS, security, metrics and threads. Spring Boot (MVC) and Quarkus do
this today, one server for the whole application; Micronaut native hosting is next, after keeping ACP
on a separate port in 0.80.0. See
[Deployment topologies](/docs/acp-java-sdk/transports#deployment-topologies) for exactly where ACP
listens in each case.

ACP over HTTP needs almost nothing from a web framework: one path, three HTTP methods, a JSON body in,
three kinds of reply out (JSON, empty, or an SSE stream), and WebSocket text frames. That's why each
framework host is small and behaves the same; see
[the full comparison](/docs/acp-java-sdk/transports#acp-over-http-needs-almost-nothing-from-a-web-framework).

**Your framework's full stack, for free.** *(Pending confirmation once the SDK's own hosts and tests
land.)* Each host sits behind the framework's own router, so Spring Security and Quarkus's HTTP
security policies and `@RolesAllowed` apply to `/acp` automatically, along with TLS, metrics and
tracing: no ACP-specific configuration needed. See
[Spring Boot](/docs/acp-java-sdk/autoconfig#the-full-stack-for-free) and
[Quarkus](/docs/acp-java-sdk/quarkus#the-full-stack-for-free) for a concrete example.

**The same annotation model works everywhere: Spring Boot, Quarkus, Micronaut, or no framework at
all.** `@AcpAgent`, `@Prompt`, `@NewSession`, and the rest carry the handlers; whatever serves the
class discovers them the same way. Plain Java needs nothing but `acp-core` and `acp-agent-support`:

```java
@AcpAgent(name = "echo-agent", version = "1.0.0")
class EchoAgent {
    @NewSession
    NewSessionResponse newSession() {
        return new NewSessionResponse(UUID.randomUUID().toString());
    }

    @Prompt
    PromptResponse prompt(PromptRequest req, SyncPromptContext ctx) {
        ctx.sendMessage("Echo: " + req.text());
        return PromptResponse.endTurn();
    }
}

AcpAgentSupport.create(new EchoAgent()).transport(new StdioAcpAgentTransport()).build().run();
```

Ten lines, no framework dependency, nothing to configure. The lower-level
[builder API](/docs/acp-java-sdk/clients-and-agents#building-an-agent-the-builder-api) is there too,
for dynamic handler registration or when a class and annotations don't fit.
**[Spring Boot](/docs/acp-java-sdk/autoconfig)**, **[Quarkus](/docs/acp-java-sdk/quarkus)**, and
**[Micronaut](/docs/acp-java-sdk/micronaut)** each serve the identical class: the framework finds the
bean and wires its transport from configuration, nothing about the class itself changes.
`acp-spring-boot-starter`/`acp-spring-boot-autoconfigure` moved from `org.springaicommunity` into
`com.agentclientprotocol`, versioned with the rest of the SDK (see the
[migration guide](/docs/acp-java-sdk/migration-0.80#spring-boot-support-moved-into-the-sdk) for the
exact coordinate and package change); Quarkus and Micronaut support are new in 0.80.0. All three are
required (non-preview) modules.

**Remote agents, for real:** many clients per agent over Streamable HTTP and WebSocket, both served on
the same `/acp` endpoint.

**Handlers run where they belong, not on a second pool the SDK bolts on:** Micronaut's virtual threads
on JDK 21+, Quarkus's own worker pool, or an executor you choose yourself on Spring Boot and plain
Java. See each framework's own "Where handlers run" section for specifics.

**Forty-plus tutorial modules and a new set of concept pages** are the fastest way to learn the
annotation model, cancellation, extension methods, elicitation, and the rest hands-on; see
[Tutorials](#tutorials) below.

**Proof, not just claims:** nearly 1,400 tests, load-testing scenarios that drive hundreds of
concurrent clients, and quality gates that fail the build on any violation, never baseline one away.
See [Quality](#quality) below.

**Start with the [quickstart](/docs/acp-java-sdk/index) or the
[tutorial](/docs/acp-java-sdk/tutorial/index).** Upgrading from 0.18.0? Read the
[migration guide](/docs/acp-java-sdk/migration-0.80) first; it has the full breaking-change list and a
checklist to work through. Curious about the wider protocol, the other language SDKs, or who else
implements ACP? See [ACP Resources](/docs/acp-java-sdk/resources).

## Features

- **[Session config options](/docs/acp-java-sdk/config-options)** replace `session/set_model`: an
  agent declares its own selectors (model choice is now just the one with `category: "model"`), plus
  a new boolean kind for simple on/off settings.
- **Cancellation and [`$/cancel_request`](/docs/acp-java-sdk/cancellation)**, in both directions, lets
  either side cancel a single in-flight request without ending the whole session; a prompt turn
  cancelled by `session/cancel` now always ends in stop reason `cancelled`, whatever the handler does.
- **[Extension methods](/docs/acp-java-sdk/extensions)** (`_`-prefixed custom requests and
  notifications) are a first-class, typed feature on every client and agent builder, not just a raw
  escape hatch.
- **[Elicitation](/docs/acp-java-sdk/elicitation)** is stable, with explicit mode-checking: an agent
  can only ask for what the client actually advertised.
- **[Terminal authentication and logout](/docs/acp-java-sdk/terminal-auth-and-logout)**: an agent can
  ask the client to run an interactive login, and advertise that it supports logging out.
- **[Streamable HTTP and WebSocket](/docs/acp-java-sdk/transports)**: a graceful shutdown window and
  clearer connection/session routing, on top of the remote-agent support described above.
- **[Forward compatibility and `_meta`](/docs/acp-java-sdk/forward-compatibility)**: former enums
  (`StopReason`, `ToolCallStatus`, and others) are open value types, several unions gained explicit
  `Unknown*` fallback variants, and every schema record carries `_meta`.
- **[Session list, close, resume and delete](/docs/acp-java-sdk/tutorial/20-session-management)**: the
  full session lifecycle from both sides, beyond the original create-and-prompt loop.

[One stability convention](/docs/acp-java-sdk/stability) covers all of it: an API is unstable if and
only if it carries `@UnstableAcpApi`. Today that's session fork and the providers methods; everything
listed above is a stable promise.

## 0.18.0 (2026-09-25)

Remote agents: the Streamable HTTP and WebSocket transport from the ACP RFD, over plain `http://` and `https://`, and a choice of Jackson 2 or Jackson 3. See [Remote agents](/docs/acp-java-sdk/index#remote-agents-over-streamable-http) for the code.

<Warning>
Three changes need attention when upgrading:

- **`acp-core` no longer contains a JSON implementation.** If you depend on `acp-core` alone, add `acp-json-jackson2` or `acp-json-jackson3`, otherwise `AcpJsonMapper.createDefault()` fails with "No AcpJsonMapperSupplier found on the classpath". `acp-agent-support`, `acp-test`, `acp-websocket-jetty` and `acp-streamable-http-jetty` already bring `acp-json-jackson2`.
- **A second client on an already-connected transport now fails at construction.** A transport instance carries exactly one session.
- **`JacksonAcpJsonMapper` built from a bare `new ObjectMapper()` is now strict about unknown fields.** Start from `JacksonAcpJsonMapper.defaultObjectMapper()` to keep the lenient behavior.
</Warning>

**Added**

- Streamable HTTP transport (RFD [streamable-http-websocket-transport](https://agentclientprotocol.com/rfds/streamable-http-websocket-transport)), contributed by @kamikaz1k (#7). `StreamableHttpAcpClientTransport` in `acp-core` talks to a remote agent over HTTP POST with SSE response streams. The new `acp-streamable-http-jetty` module provides `StreamableHttpAcpAgentTransport`, a Jetty listener that serves HTTP/SSE and a WebSocket upgrade on the same path and hosts one agent per remote connection through `AcpAgentFactory`. Header names and path match the TypeScript and Rust SDKs
- `StreamableHttpAcpServlet` is public and mountable in any Servlet 6 container (Spring Boot, Tomcat, Jetty, Undertow) at your own path; register it with async support. It serves the HTTP/SSE profile; the WebSocket upgrade needs `StreamableHttpAcpAgentTransport`
- Limits and keep-alive for the HTTP agent transport (`StreamableHttpAcpAgentTransportOptions`): POST bodies capped at 16 MiB by default, bounded WebSocket send queues and provisional `session/load` streams, a `: keep-alive` comment every 15 s on attached SSE streams, and 1,024 concurrent HTTP/2 streams per connection instead of Jetty's default 128
- HTTP/2 over plain `http://`: the client sends a bodiless GET first so that, against a server that speaks h2c, every request runs on HTTP/2; otherwise it settles on HTTP/1.1
- The Streamable HTTP client reconnects a dropped SSE stream with a short backoff; it gives up on a 404 or after three reconnects in a row that delivered nothing
- `AcpClientTransport.awaitTermination()`, implemented by the Streamable HTTP and WebSocket client transports: when the transport dies, pending and later requests fail at once with the cause instead of waiting out the request timeout
- JSON modules (#12): the Jackson 2 mapper moved into `acp-json-jackson2`, and `acp-json-jackson3` adds `Jackson3AcpJsonMapper` on Jackson 3 (3.1.5, the version Spring Boot 4.1 manages). Both write the same bytes on the wire. Proposed by @bengbengbalabalabeng
- Deterministic JSON mapper selection by `AcpJsonMapperSupplier.priority()`: with both modules present Jackson 3 wins, and an application's own supplier wins over both. The system property `acp.json.mapper.supplier` names one explicitly
- `CancelNotification` carries `_meta`; `AcpSyncClient(AcpAsyncClient)` is public, so both APIs can share one session

**Changed**

- Breaking: `acp-core` depends on `jackson-annotations` only, not on `jackson-databind` or `jackson-core` (#12). `JacksonAcpJsonMapper` keeps its package and name
- Single-turn enforcement is per logical session (keyed by `sessionId`), because one HTTP connection carries many sessions. Stdio and WebSocket agents behave as before (#7, #9)
- Unknown-field policy moved from the schema records to the mapper (#10). The default mapper stays lenient and logs each ignored property at DEBUG; a strict mapper you pass in is now honored. Reported by @KallivdH
- Request timeouts run on one shared library-owned daemon timer instead of a thread pool per session

**Deprecated**

- `WebSocketAcpAgentTransport` (`acp-websocket-jetty`) is deprecated for removal. It serves a single WebSocket client; `StreamableHttpAcpAgentTransport` serves the WebSocket upgrade for any number of clients, and `WebSocketAcpClientTransport` clients connect to it unchanged

**Fixed**

- A second `AcpClient.async(transport)` or `AcpClient.sync(transport)` on the same stdio transport started a second agent process whose requests could only time out. This was the Spring Boot autoconfiguration failure reported in June 2026. The stdio transport now refuses a second `connect()`, and sessions surface connect failures instead of dropping them
- A second prompt on a session could be rejected with `-32000` or hang under CPU contention (#14): the prompt lock is now released before the response is published. Reported by @krickert
- `WebSocketAcpAgentTransport` wrote frames without waiting for the previous write, and could throw a `NullPointerException` on close
- The agent session reads `sessionId` from typed `PromptRequest` and `CancelNotification` params, so in-process transports match cancels correctly

## 0.17.0 (2026-08-28)

Wire-format correction. No public API change: every constructor and accessor is unchanged, and the ACP surface is identical to 0.16.1.

- Fix the duplicate discriminator on the wire: every polymorphic type wrote its `type` property twice, so `new TextContent("hello")` serialized to `{"type":"text","type":"text","text":"hello"}` and every `session/prompt` carried a duplicate JSON key. Jackson-based peers accept duplicates; a strict parser rejects the message. The type id is now written once and is populated on deserialization (previously `null`). 27 records across 6 hierarchies

## 0.15.0 (2026-08-21)

Correctness and supply-chain hygiene. No protocol or public API changes — a drop-in upgrade from 0.14.0.

- Fix non-deterministic notification ordering — notifications are serialized through a sink drained by `concatMap`, preserving arrival order (thanks @ljiro)
- Drain queued notifications on graceful close instead of discarding them; `closeGracefully()` now waits for the drain, bounded by the session `requestTimeout`
- Distinguish expected from anomalous notification-sink emission failures in logging
- Security: Jackson 2.21.2 → 2.21.5 and Jetty 12.0.14 → 12.0.37, clearing 17 known advisories (5 high) in the published dependency closure
- Ship the verbatim Apache License 2.0, and package LICENSE and NOTICE under `META-INF` in every artifact
- Run the integration tests — three `*IT` classes existed but were never executed by `mvn verify`
- Pin GitHub Actions to commit SHAs; bound workflow jobs to 30 minutes
