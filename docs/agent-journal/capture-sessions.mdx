---
title: "Capture SDK Sessions"
description: "Record Claude Code, Gemini CLI, Grok, Codex, Antigravity, and Junie results with Agent Journal 1.11.0"
---

Agent Journal provides six vendor adapters that write compatible core events and portable traces.

The Claude and Gemini adapters parse a typed SDK object: Claude consumes the [Claude Agent SDK for Java](/projects/claude-agent-sdk) and Gemini the `gemini-cli-sdk` published with [Agent Client](/projects/agent-client).
Both require a Java 21 runtime, because those SDK dependencies are published as Java 21 bytecode.

The Grok, Codex, Antigravity, and Junie adapters parse their CLI's durable JSONL directly and carry no vendor SDK dependency, so they run on Java 17 like `journal-core`.
All four produce an ordered tool trajectory; Gemini does not.

Every module turns one agent call into the same journal shape: a run with a prompt event, one `llm_call` with the call's token usage and cost, one `tool_call` per tool use with the tool's own input map, and a `step_cost` per step in the analysis log.
The differences are in what each CLI reports:

| Provider | Source read | Tool trajectory | Cost | Sub-agents |
|---|---|---|---|---|
| Claude Code | the CLI's `stream-json` output, through `claude-code-sdk` | yes, with per-turn usage and the stable `tool_use` id as step id | reported by the CLI, split per step | **captured as linked runs** (1.11.0) |
| Codex | the durable rollout file(s) | yes; tool calls classified from their payload, `function_call` arguments kept verbatim | not reported by Codex (`costAvailable=false`) | **captured as linked runs** (1.11.0) |
| Gemini CLI | the SDK's turn-level result | turn level only | reported | no |
| Grok CLI | `streaming-json` output | yes | reported | no |
| Antigravity | streaming JSON | yes | per step where reported | no (the stream carries pointers only) |
| Junie | the session's `events.jsonl` | yes, with per-call cost reconciling to the session total | reported | no |

Sub-agent capture for Claude Code and Codex has its own guide: [Sub-agent Capture](/docs/agent-journal/subagent-capture).
Each file written by the library carries a schema-version header and, since 1.11.0, the producer version, so a reader can tell which release wrote a record.

## Claude Code

Add the adapter:

```xml
<dependency>
    <groupId>io.github.markpollack</groupId>
    <artifactId>claude-code-capture</artifactId>
    <version>1.11.0</version>
</dependency>
```

`SessionLogParser` converts an `Iterator<ParsedMessage>` from the Claude Code SDK into a `PhaseCapture`.
Despite its name, it reads the live SDK message stream, not a session log file.
The six-argument overload also writes a portable trace and controls modeled and raw content independently:

```java
import io.github.markpollack.claude.agent.sdk.parsing.ParsedMessage;
import io.github.markpollack.journal.claude.PhaseCapture;
import io.github.markpollack.journal.claude.SessionLogParser;
import io.github.markpollack.journal.trace.TraceContentMode;
import io.github.markpollack.journal.trace.TraceRawMode;
import java.nio.file.Path;
import java.util.Iterator;

PhaseCapture phase = SessionLogParser.parse(
        response,
        "implement",
        promptText,
        Path.of(".agent-journal/traces/implement.jsonl"),
        TraceContentMode.TRUNCATED,
        TraceRawMode.NONE);
```

Here, `response` is an `Iterator<ParsedMessage>` returned by the SDK and `promptText` is the exact prompt or `null`.

Record the capture into a durable journal with `RunRecorder`:

```java
import io.github.markpollack.journal.Journal;
import io.github.markpollack.journal.claude.RunRecorder;
import io.github.markpollack.journal.storage.JsonFileStorage;
import java.nio.file.Path;

Journal.configure(new JsonFileStorage(Path.of(".agent-journal")));

try (RunRecorder recorder = new RunRecorder(
        Journal.run("capture-experiment").agent("claude-code").start())) {
    recorder.recordPhase(phase);
    recorder.finish();
}
```

Call `finish()` on the success path.
Since 1.11.0 only `finish()` records a completed run: `close()` cannot tell a normal exit from an exception leaving the block, so a recorder closed without `finish()` ends its run `CRASHED`.
A plain `Run` is unchanged; its `close()` still ends it `FINISHED`.

The recorder writes execution events to `events.jsonl` and per-step cost attribution to `analysis.jsonl`.
It fails at finish when it produced derived events but the configured backend does not persist them durably, and it ends the run before throwing.
Call `lenient()` only when losing the derived stream after process exit is intentional.

### Record once

To record an execution at most once per experiment and storage root, even across a restart, use `recordOnce` instead of creating the run yourself:

```java
import io.github.markpollack.journal.claude.RunRecorder;
import io.github.markpollack.journal.storage.SourceRecordings;

SourceRecordings.Outcome outcome = RunRecorder.recordOnce(
        "capture-experiment", phase, builder -> builder.agent("claude-code"));
```

`outcome.runId()` is the run that records the execution and `outcome.recordedNow()` is `false` when an earlier, complete recording was found.
The run carries the execution's key (`capture.sourceKind`, `capture.sourceKey`); the same source processed again writes nothing, a later prompt of the same session records normally, and an earlier recording that has not ended or ended with an error fails explicitly.
`recordOnce` needs a capture with a session id and per-turn message ids, which `parse` over the live SDK stream provides.

### Multi-prompt sessions

Claude Code reports `total_cost_usd`, `modelUsage` and `duration_api_ms` on every result line as the **session's running total**, while `usage`, `duration_ms` and `num_turns` cover the query alone.
A caller that records one phase per prompt in one session rebases each later capture onto the previous one:

```java
PhaseCapture first = SessionLogParser.parse(firstResponse, "plan", planPrompt);
PhaseCapture secondRaw = SessionLogParser.parse(secondResponse, "implement", implementPrompt);
PhaseCapture second = SessionLogParser.withSessionBaseline(secondRaw, first);
```

The returned capture carries the query's own cost, per-model costs and API time as the difference from the previous capture of the same session id, keeps the running totals in `sessionCost()`, and is recorded with `costBasis=session_delta` and `sessionCumulativeCostUsd` in the LLM call's metadata.
It never subtracts across session ids and leaves a capture unchanged when the counters restarted.
`parse` itself is unchanged, so a record without `costBasis` from a later prompt carries the running total.

## Gemini CLI

Add the adapter:

```xml
<dependency>
    <groupId>io.github.markpollack</groupId>
    <artifactId>gemini-cli-capture</artifactId>
    <version>1.11.0</version>
</dependency>
```

`GeminiSessionParser` converts the Gemini SDK's synchronous `QueryResult` into a `GeminiPhaseCapture`:

```java
import io.github.markpollack.agents.geminisdk.types.QueryResult;
import io.github.markpollack.journal.Run;
import io.github.markpollack.journal.gemini.GeminiPhaseCapture;
import io.github.markpollack.journal.gemini.GeminiRunRecorder;
import io.github.markpollack.journal.gemini.GeminiSessionParser;

GeminiPhaseCapture phase = GeminiSessionParser.parse(
        result, "query", "summarize the repository");

new GeminiRunRecorder(run).recordPhase(phase);
```

Here, `result` is a `QueryResult` and `run` is an open Agent Journal `Run`.
Configure `JsonFileStorage` if the derived `StepCostEvent` must survive process exit.

Gemini's typed SDK exposes result-level text, usage, cost, duration, model, and status, but it does not expose per-tool calls.
The adapter therefore records one turn-level step and does not invent tool detail.
It has no `TraceRawMode` because the typed Gemini message does not retain a verbatim wire envelope.

## Grok CLI

Add the adapter:

```xml
<dependency>
    <groupId>io.github.markpollack</groupId>
    <artifactId>grok-cli-capture</artifactId>
    <version>1.11.0</version>
</dependency>
```

`GrokSessionParser` reads Grok's ACP-shaped `streaming-json` output from a file or a `BufferedReader`:

```java
import io.github.markpollack.journal.Run;
import io.github.markpollack.journal.grok.GrokPhaseCapture;
import io.github.markpollack.journal.grok.GrokRunRecorder;
import io.github.markpollack.journal.grok.GrokSessionParser;
import java.nio.file.Path;

GrokPhaseCapture phase = GrokSessionParser.parse(
        Path.of("grok-stream.jsonl"), "implement", promptText);

new GrokRunRecorder(run).recordPhase(phase);
```

The parser pairs `tool_call` and `tool_call_update` records by `toolCallId`, keeping both the tool name Grok reports and its ACP semantic kind.
Grok's stream carries a real session cost in `end.total_cost_usd` but no durable join from a turn to the tools it ran, so the session total is retained and attributed evenly across the captured tool steps.

## Codex CLI

Add the adapter:

```xml
<dependency>
    <groupId>io.github.markpollack</groupId>
    <artifactId>codex-cli-capture</artifactId>
    <version>1.11.0</version>
</dependency>
```

`CodexSessionParser` reads a durable Codex rollout JSONL file, or, since 1.11.0, the root rollout together with the child rollouts of the sub-agents it started:

```java
import io.github.markpollack.journal.Run;
import io.github.markpollack.journal.codex.CodexPhaseCapture;
import io.github.markpollack.journal.codex.CodexRunRecorder;
import io.github.markpollack.journal.codex.CodexSessionParser;
import java.nio.file.Path;

CodexPhaseCapture phase = CodexSessionParser.parse(
        Path.of("rollout.jsonl"), "implement", promptText);

new CodexRunRecorder(run).recordPhase(phase);
```

When the session started sub-agents, collect the root and child rollout files and pass them as one `CodexRollouts`; each child becomes a linked run.
`CodexRunRecorder.recordOnce` records the execution at most once, keyed by the root thread id.
See [Sub-agent Capture](/docs/agent-journal/subagent-capture) for the collection, linkage, status and accounting rules.

```java
import io.github.markpollack.journal.codex.CodexRollout;
import io.github.markpollack.journal.codex.CodexRollouts;
import java.nio.file.Files;
import java.util.List;

CodexRollout root = new CodexRollout(rootThreadId, null, rootPath.toString(), Files.readAllLines(rootPath));
CodexRollout child = new CodexRollout(childThreadId, rootThreadId, childPath.toString(), Files.readAllLines(childPath));

CodexPhaseCapture tree = CodexSessionParser.parse(
        new CodexRollouts(List.of(root, child)), "implement", promptText);

SourceRecordings.Outcome outcome = CodexRunRecorder.recordOnce(
        "capture-experiment", tree, builder -> builder.agent("codex"));
```

Codex records most tool invocations under the outer function name `exec`, which would collapse every step into one undifferentiated name.
The parser deliberately classifies the nested `payload.input` call instead, extracting `exec_command` arguments without evaluating them and assigning semantic names such as `Search`, `Read`, `Inspect`, `Test`, `Build`, and `Git`.

<Note>
The classifier is conservative about shell syntax.
Aliases, shell functions, quoted operators, and work hidden behind an interpreter fall back to `Shell`.
The raw input and command are retained on the record, so callers can reclassify them later.
</Note>

Codex rollout token counts, including cached and reasoning tokens, are preserved.
Since 1.11.0 `inputTokens` excludes cached input, as for every other provider; an older value converts exactly by subtracting `cacheReadTokens`.
A `function_call` tool call is recorded under its own name with its arguments kept verbatim, and a tool call that exited with code 0 is not marked failed.

## Antigravity CLI

Add the adapter:

```xml
<dependency>
    <groupId>io.github.markpollack</groupId>
    <artifactId>antigravity-cli-capture</artifactId>
    <version>1.11.0</version>
</dependency>
```

`AntigravitySessionParser` reads Antigravity's streaming JSON:

```java
import io.github.markpollack.journal.Run;
import io.github.markpollack.journal.antigravity.AntigravityPhaseCapture;
import io.github.markpollack.journal.antigravity.AntigravityRunRecorder;
import io.github.markpollack.journal.antigravity.AntigravitySessionParser;
import java.nio.file.Path;

AntigravityPhaseCapture phase = AntigravitySessionParser.parse(
        Path.of("antigravity-stream.jsonl"), "implement", promptText);

new AntigravityRunRecorder(run).recordPhase(phase);
```

The parser pairs active and terminal updates by `step_index` and handles both `DONE` and `ERROR` steps, recording parameters, output or error text, duration, and terminal token usage.
Stable identities are derived from the conversation and step positions.

## Junie CLI

Add the adapter:

```xml
<dependency>
    <groupId>io.github.markpollack</groupId>
    <artifactId>junie-cli-capture</artifactId>
    <version>1.11.0</version>
</dependency>
```

`JunieSessionParser` reads Junie's durable session trace, `~/.junie/sessions/<sessionId>/events.jsonl`, from a file or a `BufferedReader`:

```java
import io.github.markpollack.journal.Run;
import io.github.markpollack.journal.junie.JuniePhaseCapture;
import io.github.markpollack.journal.junie.JunieRunRecorder;
import io.github.markpollack.journal.junie.JunieSessionParser;
import java.nio.file.Path;

JuniePhaseCapture phase = JunieSessionParser.parse(
        Path.of("events.jsonl"), "implement", promptText);

new JunieRunRecorder(run).recordPhase(phase);
```

Junie re-emits the same `stepId` as a step's status progresses, so the parser folds every update for a step into one record rather than counting lines.
Junie reports no tool name; the record keeps the block event kind that described the step (`TerminalBlockUpdatedEvent`, `ViewFilesBlockUpdatedEvent`, `FileChangesBlockUpdatedEvent`, or `ToolBlockUpdatedEvent`) and maps it to an execute, read, edit, or other tool kind.
The parser reads both the plain-CLI and the Agent Client Protocol shapes of the trace.

<Note>
Junie's trace includes an event carrying the agent's environment variables, unredacted.
The parser deliberately drops that event, so none of it reaches the capture or the journal.
</Note>

Junie prices every LLM call, and the per-call costs reconcile to the session total, so the capture carries a real cost.
It reports no thinking-token count, so the capture has no thinking-token field; thinking text is captured when the trace contains it.

## Cost provenance

Neither Codex nor Antigravity reports monetary cost in these streams.
Their cost records are zero-valued and explicitly marked `costAvailable=false` with an `unreported` source, so a downstream reader can distinguish "this run cost nothing" from "this CLI never said."
Junie does report cost: its records are marked `costAvailable=true` with a `reported` source when the trace carries per-call costs.
Like Grok, Junie reports a session total but no per-step cost, so its per-step `StepCostEvent` shares are an even split of that total.
A Grok, Codex or Junie tool call whose duration was not measured records `durationMs` as -1 since 1.11.0 (earlier versions wrote 0).

## Portable trace modes

`TraceContentMode` controls content bodies on modeled trace lines:

| Mode | Modeled content behavior |
|---|---|
| `FULL` | Writes complete assistant text, thinking text, and tool-result content |
| `TRUNCATED` | Default; caps each modeled content body at 60,000 characters |
| `LENGTHS` | Omits those modeled content bodies and records their lengths |

`TraceRawMode` is Claude-only and orthogonal:

| Mode | Raw vendor messages |
|---|---|
| `NONE` | Default; no raw vendor-message lines |
| `FULL` | Writes each available vendor message as an unredacted `raw` line |

<Warning>
All trace modes require a data-handling decision.
The capture record and journal events can contain the caller-supplied prompt text.
Tool inputs are present on portable `tool_use` lines even in `LENGTHS` mode.
`TRUNCATED` and `FULL` portable traces can include assistant text, file contents, tool results, and command output.
`TraceRawMode.FULL` adds the complete available vendor message and can include fields omitted from the typed model.
Treat trace and journal files as sensitive, restrict filesystem access, and keep them out of version control.
</Warning>

## Two schemas

Do not conflate the two JSONL formats:

- Canonical journal streams use `@type` and currently have schema version 1.
- Portable capture traces use `type`, `ts`, and `seq` and currently have schema version 2.

Both formats have their own header and evolution contract.
