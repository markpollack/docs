The [Agent Judge Tutorial repository](https://github.com/markpollack/agent-judge-tutorial/tree/106ca35a74ebdd9995329cb0bde63d66a9e7e8ed) is the canonical sample suite.
The eleven fundamentals modules are small executable Maven projects compiled against Agent Judge 0.17.0.
The fundamentals commands below select the historical tested 0.17.0 revision. The migrated PetClinic path uses Agent Eval 0.18.0 in a separate reactor.

```bash
git clone https://github.com/markpollack/agent-judge-tutorial.git
cd agent-judge-tutorial
git checkout 106ca35a74ebdd9995329cb0bde63d66a9e7e8ed
./mvnw install
./mvnw exec:java -pl module-01-oracle-boundary
```

The `install` step is needed once: later modules reuse judges written in earlier ones, and `exec:java` resolves those from the local repository.
Run every module from the repository root — the demos resolve `test-workspace` relative to where Maven was launched.

No module needs an API key or a live model endpoint.
The first build downloads Maven dependencies; prepare the caches before attempting an offline run.

## The fundamentals subject

Every fundamentals module judges the same change.
`test-workspace` is a small Maven project whose `HelloController` delegates to a service and returns a record — the codebase's idiom.
An agent was asked to expose a sales report endpoint and added `ReportController`, which opens its own JDBC connection, concatenates SQL from request parameters, builds JSON by hand, swallows the exception, and closes nothing.

It compiles. It is in the right package. It is named correctly. It has the requested method.

## The fundamentals sequence

The modules are ordered by the evaluation problem each one creates, not by the next API.

| Module | The problem it introduces |
|---|---|
| 01 | A criterion with no expected value. [Known oracle vs. judgment oracle](https://github.com/markpollack/agent-judge-tutorial/tree/106ca35a74ebdd9995329cb0bde63d66a9e7e8ed/module-01-oracle-boundary) |
| 02 | The compiler and JUnit are already oracles; Agent Judge carries their answers |
| 03 | A measurement is not an acceptance decision, and a score is not a status |
| 04 | Writing a judge: task → criterion → evidence → judgment |
| 05 | A derived oracle: several objective facts, one finding, every part kept |
| 06 | Composing requirements without collapsing them into a number |
| 07 | Inside the judgment oracle: prompt template, model, classifier |
| 08 | When aggregation *is* right: several estimates of one property |
| 09 | A judge that could not run must not improve the result |
| 10 | The same bar, applied to a Koog agent |
| 11 | The same bar, applied to a LangChain4j result |

A twelfth module, `judge-junit`, is a small bridge turning an Agent Judge outcome into a useful JUnit assertion failure.

## Three kinds of oracle

The sequence exists to make one distinction concrete.

**Known.** An exact or deterministic answer exists — compilation succeeds, tests pass, a file exists, API compatibility holds, coverage clears a threshold.
Use ordinary Java tooling or a deterministic judge. Modules 01–03.

**Derived.** No single expected value exists, but several objective facts settle the question — a class is where the layout says it should be, a patch touched only allowed files, coverage improved without deleting tests.
Still deterministic, just not one assertion. Module 05.

**Judgment.** The property itself requires interpretation — does this fit the conventions of this codebase, did the review identify the important risks, is the proposed API sensible, did the implementation satisfy the user's intent.
This is where a model-backed judge earns its existence. Modules 01 and 07.

## The fundamentals live path

Four modules, roughly ten minutes, in directory order:

```bash
./mvnw exec:java -pl module-01-oracle-boundary      # where JUnit stops
./mvnw exec:java -pl module-02-build-and-tests      # the oracles you already trust
./mvnw exec:java -pl module-03-coverage-evidence    # a measurement is not a decision
./mvnw exec:java -pl module-06-definition-of-done   # would you merge this?
```

It ends here:

```
  CRITERION          ORACLE     STATUS
  ------------------ ---------- ------
  build              known      PASS
  tests              known      PASS
  coverage           known      FAIL
  package-structure  derived    PASS
  architectural-fit  judgment   FAIL

  done: false
```

Modules 02, 03 and 06 run real Maven builds; run each once before presenting so dependencies are warm.

## What to observe

**Module 01** keeps four criteria in plain `assertTrue` on purpose.
Agent Judge appears only for the criterion that has no expected value, and the judgment it returns carries one `Check` per criterion rather than an average — five failures out of six do not become `0.17`, because a number cannot name the criterion that binds.

**Module 03** separates three things a score normally collapses: the measurement (`100.00% → 36.00%`), the normalized score (`0.0`, which floors and so cannot distinguish a 1-point drop from a 64-point one), and the status (`FAIL`, against a bar written down with its derivation).
Pointed at a workspace where no build ran, the judge returns `ERROR` — not `FAIL`, and not `0.0`.

**Module 06** is the distinction the library most needs stated.
Five criteria are not five opinions about one thing, so `3 of 5 = 0.60` is the wrong rule.
It also counts invocations to show that `Judges.allOf` short-circuits after 3 of 5 judges, and runs the conjunction over an empty list to show that `allMatch` returns `true` there.

**Module 08** is the case where a jury is correct: three reviewers independently estimating one property, disagreeing two to one.
Majority returns `FAIL`; consensus returns `ABSTAIN`, because a split vote is indeterminate rather than negative.

**Module 09** runs one panel under all four error policies.
Three of the four report `PASS` for a run in which a required criterion was never evaluated.
It also distinguishes `ABSTAIN` (an applicable question left undecided) from `NOT_APPLICABLE` (a declared exclusion); an undeclared exclusion in a jury becomes `ERROR`.

**Modules 10 and 11** execute real adapter code with deterministic framework objects, so bridge construction and metadata extraction stay verifiable offline.

## Credential-free model-backed judges

Modules 01 and 07 use a fixture `JudgeModel` that supplies fixed replies.
The source says so rather than dressing the fixture up as a recording: a fixture cannot tell you a judge is *right*, only that the wiring around it is.

Everything else on the path is real — the prompt is rendered from the actual `JudgmentContext`, the classifier parses free text into a `Judgment` with `Check`s, and swapping the model for `SpringAiJudgeModel` is a one-line change.

An unrecorded subject returns `ERROR` rather than a default `PASS`.
A stand-in that approves what it has not seen is a judge that cannot fail.
