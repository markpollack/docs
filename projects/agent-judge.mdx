**The agent says it is done. Should you merge?**

Agent Eval (in the Agent Judge repository) is a Java 21 library for evaluating work against
requirements set before execution. Configure a `Judge` with its requirement, runtime and evidence,
then call `judge()`. Configure a `Jury` with the selected requirements and call `vote()`.
Retain the complete result before deciding whether the application may rely on it.

These guides cover source revision
[`904c1983c3c919b873ca03beb7e321759580ee14`](https://github.com/markpollack/agent-judge/tree/904c1983c3c919b873ca03beb7e321759580ee14),
version `0.18.0-SNAPSHOT`. This is a source-build adoption path; it does not announce a published
0.18 release. [Getting started](/docs/agent-judge/getting-started) installs that exact source into
the standard Maven repository, with isolation optional. The separate fundamentals tutorial still uses released 0.17.0.

## Requirements, evidence and execution

Keep using javac, JUnit and static analysis for questions they can settle. Use a model or agent
when checking a written requirement needs interpretation. Prepared evidence is supplied explicitly;
workspace, tools and timeout are configured on an investigative backend.

`EarsJudge` and `Rfc2119Judge` assess one actual requirement. `EarsJury` and `Rfc2119Jury` assess a
selected roster. A generated investigative roster enters its backend once for the whole roster;
that backend can make several internal model and tool calls. A structured runtime executes once
per requirement and retains those individual invocation owners.

[The PetClinic case study](/docs/agent-judge/petclinic-case-study) uses the same unchanged subject:

| Question | Retained answers | Verdict conclusion |
|---|---|---|
| Does the candidate build and pass its existing tests? | Real deterministic build | PASS Judgment |
| Do the selected six EARS requirements hold? | 6 PASS | PASS |
| Do all 52 EARS requirements hold? | 51 PASS; UC6-AC41 ABSTAIN | INCONCLUSIVE |
| Do all 13 architectural requirements hold? | 5 PASS; 8 FAIL | FAIL |

The model-backed rows replay archived responses. Fresh replay verifies the configured public
caller and retention, rather than establishing new model findings about the subject.

## Keep the result and the reliance decision

A `Judgment` keeps PASS, FAIL, ABSTAIN, NOT_APPLICABLE and ERROR distinct. A `Verdict` additionally
retains the roster, actual requirement associations, child attempts and original results.
Native facts and invocation ownership stay attached; absent recorded usage remains unknown.
A refused native result preserves its complete original, including its own Checks and invocations.

Application policy is a separate decision. Withholding reliance on a PASS Verdict does not rewrite
its conclusion. Producer AssertJ stages evaluate once, cache the complete result or failure,
and can apply policy once. V6 storage retains the corresponding EvaluationResult. Retained reads
and assertions execute no producers or policies.
