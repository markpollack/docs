**The agent says it is done. Should you merge?**

Agent Judge is a Java 21 library for evaluating whether an agent's work meets the requirements you set for it.
An eval starts with a definition of good, gathers evidence from the result, and decides whether that bar was met.
The criteria are set before the work is judged.

## Extend the testing discipline you already use

JUnit handles assertions where you know how to write the oracle: an expected value for `assertEquals`, or a rule for `assertTrue`.
Agent Judge extends that testing discipline to criteria whose answers need richer evidence or judgment.

Keep using javac, JUnit, ArchUnit, and static analysis for questions they can settle.
Use a model when establishing whether the implementation meets a written requirement needs interpretation.
When that check can be expressed reliably with deterministic tooling, give it back to that tooling.

## Turn written requirements into a JUnit gate

`EarsJudge` checks written EARS acceptance criteria against an implementation.
`Rfc2119Judge` checks architectural constraints written with RFC 2119 keywords such as `MUST` and `MUST NOT`.
Both are available in `agent-judge-ai-core` in Agent Judge 0.17.0.
**The model assesses each requirement; the code decides the verdict.**

This is the JUnit test from the [PetClinic tutorial's behavioral merge gate](https://github.com/markpollack/agent-judge-tutorial/blob/main/case-studies/spec-driven-petclinic/module-03-ears-usecase/src/test/java/io/github/markpollack/judge/tutorial/ears/ShouldIMergeBehaviorDemo.java), with class setup and imports omitted:

```java
@Test
@DisplayName("Should I merge? All 52 UC6 requirements must PASS")
void shouldMergeUc6Behavior() {
    var requirements = EarsCriterion.from(CRITERIA);

    var judge = EarsJudge.create("appointment-lifecycle", requirements, model);

    assertPass(judge, context);
}
```

`CRITERIA` points to the specification, `context` identifies the implementation under evaluation, and `model` replays a committed response from a real agent run.
The tutorial's [`JudgeAssertions.assertPass`](https://github.com/markpollack/agent-judge-tutorial/blob/main/judge-junit/src/main/java/io/github/markpollack/judge/junit/JudgeAssertions.java) helper requires `PASS` and reports the actual status, reasoning, and checks that did not pass in the JUnit failure message.

## Same code, different questions

The conference case study evaluated a PetClinic implementation against requirements written before the code existed.
The implementation stayed unchanged across these checks:

| Evaluation | Result |
|---|---|
| Does it build and pass its existing tests? | `PASS` |
| Does it satisfy all 52 acceptance criteria? | 51 established, `UC6-AC41` unsettled: `ABSTAIN` |
| Does it satisfy the 13 architectural constraints? | 5 passed, 8 failed: `FAIL` |

**The JUnit gate above goes red.** Every required criterion must be established to pass; the unresolved one remains named and visible.
`ABSTAIN` means the question is still open, and that is enough to block this merge policy.
The architectural failures identify places to investigate; establishing their consequences is a separate step.

The tutorial also has regression tests that assert these recorded outcomes and pass when replay reproduces them.
The merge gate asks whether the application met the bar; the regression test asks whether the evaluator reproduced the expected result.

## Read the outcome

The central result is status-first.
Every `Judgment` has a `PASS`, `FAIL`, `ABSTAIN`, `NOT_APPLICABLE`, or `ERROR` status, while a normalized score and classification label are independent optional facts.
Result metadata is restricted to portable values so judgments can cross JSON and process boundaries reliably.

## Bring the same evaluation policy to each runtime

Spring AI, LangChain4j, Koog, and AgentClient each have their own execution model.
Each Agent Judge bridge converts framework output into a `JudgmentContext`, after which the same judges and juries evaluate it.

Adapters preserve native output, model identity, token usage, timing, and tool evidence in a shared `JudgmentContext`. The judges and jury policy above that boundary do not change when the producing runtime does.

| Runtime | Evaluation entry point |
|---|---|
| Spring AI | `SpringAiEvaluator` |
| LangChain4j | `LangChain4jEvaluator` |
| Koog | `KoogEvaluator` |
| CLI agents through AgentClient | `AgentClientEvaluator` |

## Install 0.17

```xml
<dependency>
  <groupId>io.github.markpollack</groupId>
  <artifactId>agent-judge-core</artifactId>
  <version>0.17.0</version>
</dependency>
```

Add only the family and bridge modules that your application uses.
For EARS and RFC 2119 judges, add `agent-judge-ai-core` as shown in the [requirements judges guide](/docs/agent-judge/requirements-judges#run-the-examples).
